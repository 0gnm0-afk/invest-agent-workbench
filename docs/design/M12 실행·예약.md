## 앞 절반 — 설명서

### 1. 하는 일 (세 줄 이내)

대시보드와 일봉 수집을 시작하는 입구를 남은 기능에 맞춘다.
같은 작업의 중복 실행을 막고 실패·재시도 기록을 남긴다.
앱의 자동 계좌 조회를 없애며, 아침 예약 재개는 6단계에 남긴다.

### 2. 입력과 출력

| 입력 | 출력 |
|---|---|
| 시작 방식·시각·이전 실행 기록 | 새로 시작·기존 작업 재사용·대기·실패 |
| 수집 완료 증거와 감시·전송 결과 | 수집·감시·전송을 구분한 실행 기록 |
| 중복 요청 또는 명시적 재시도 | 중복 차단, 이전 시도를 보존한 재시도 |

일봉은 전 종목을 수집한다. 보유 종목의 가격 위험은 자동 감시하고, 미보유 종목의 기술 신호·시나리오는 명시 등록한 것만 감시한다. 조건 판정은 M07이 맡는다.

### 3. 저장 위치 (C1 소유 테이블·파일)

M12 소유 업무 DB는 없다. 실행 주소·잠금은 `runtime/dashboard/`, 날짜별 시도는 `runtime/dashboard-daily/`, 예약 실행 기록은 `runtime/morning-schedule/`에 둔다. M13에는 이 파일의 보존 범위를 전달한다. 검사 자료와 결과는 OS 임시 폴더에만 만든다.

### 4. 다른 모듈과의 연결 (§8 개정 계약 적용)

- **C1·C6·C7:** DB 쓰기는 소유 모듈의 함수로 한다. MCP 도구는 M09, 화면·HTTP는 M10 소유다.
- **C5:** 보유 가격 위험은 자동, 미보유 기술 신호·시나리오는 명시 등록이다(§8.1·8.4).
- **C8:** M00 실행기로 가짜 자료를 검사한다. 외부 네트워크와 운영 자료·인증 접근은 막고, 임시 자료의 내부 통신과 보호 장치를 물려받은 시험용 자식 프로세스는 허용한다(§8.2).
- **C9:** M03의 수집 완료 영수증으로 실행 성공을 판단한다(§8.3).

계좌는 세션 MCP 조회 결과를 M08에 저장한다. 경고·감시는 마지막 저장 관측과 그 기준 시각을 사용한다. 전송 여부를 계좌 조회에 묶지 않는다.

### 5. 이번 개편에서 바뀌는 것 / 그대로인 것 / 없어지는 것

| 구분 | 내용 |
|---|---|
| 바뀌는 것 | 수집 성공의 근거를 스크리닝 결과에서 M03 영수증으로 바꾸고, 시작 화면의 종료 메뉴 이름을 정리한다. |
| 그대로인 것 | 중복 방지·한국 시각·완료 거래일·명시적 재시도·이전 기록. 예약은 사용자 중지 상태다. |
| 없어지는 것 | 앱의 자동 계좌 조회, 계좌 조회와 전송의 결합, 종료 기능을 다시 요구하는 연결. 기존 계좌·사이클 자료는 보존한다. |

### 6. 쓰는 법 (세션에서·대시보드에서)

세션에서는 실행 결과와 실패 이유를 확인하고 필요한 재시도만 요청한다. 대시보드는 같은 모드로 열면 기존 서버를 재사용한다. 저장 자료 보기와 갱신 실행은 구별한다. 실제 예약·운영 대시보드 확인은 별도 운영 적용 때 한다.

### 7. 사용자가 직접 확인하는 방법 (5단계 검수에 그대로 쓴다)

M00의 M12 검사 결과에서 다음 가짜 사례를 확인한다.

1. 같은 날 중복 실행은 한 번만 처리하고, 실패 뒤 재열기만으로 재수집하지 않는다.
2. 계좌 조회 없이 저장 관측으로 감시하며 기준 시각이 표시된다. 전송 실패는 수집 성공을 바꾸지 않는다.
3. 금지 접근·차단·건너뜀·미확인이 통과 수에 섞이지 않는다. 실제 예약을 재개했다는 뜻은 아니다.

## 뒤 절반 — 작업 지시서

### 1. 범위와 목표

**확정:** 조 5에서 M00 및 조 1~4의 반영본을 받아 `launch/`의 실행 수명·호출 순서·잠금과 합성 검사를 정리한다. M13과 병렬이며 같은 파일을 고치지 않는다.

- **§8.3 / C9:** M03이 `{target_trade_date, completed, failed, status, provenance, sha256}`를 제공하고 M12가 성공 판정에 쓴다. M01은 조 1에서 `priority-review.json` 의존을 줄이는 최소 변경만 한다. 이후 `market/daily.py`는 M03, `launch/daily.py`는 M12 소유다. 실제 필드 대응·자료형·해시 대상의 공백은 M12-Q05이며 임의로 확정하지 않는다.
- **§8.1·8.6:** `DailyLaunch`와 예약의 자동 계좌 조회 경로를 제거한다. `accounts=True`로 실제 조회가 복구되는 경로를 남기지 않는다. 계좌 관측 저장·완전성·lease는 M08이 유지하며, M12는 마지막 저장 관측을 사용하는 M07 함수를 호출한다. 전송은 계좌 조회 플래그 대신 M07의 적격 사건·전송 설정에 따른다.
- **§8.6:** `register-morning-task.ps1`은 6단계까지 **수정하지 않는다**. 시작 메뉴의 섹터·스크리닝·계좌 화면 이름은 M12가 정리한다.
- **§8.2 / C8:** 외부 DNS·외부 connect, 운영 runtime·DB·인증 파일·Windows 사용자 환경변수 접근은 0이다. OS 임시 workspace의 합성 파일·DB, `127.0.0.1`·socketpair, 같은 가드를 상속받는 임시 fixture 자식 프로세스만 허용한다. 실제 운영 확인은 §9로 분리한다.

**권장:** `once(...)`, `public(...)`, `run_scheduled(...)`, `exit_code(...)`의 형태는 유지하고 필요한 경계에 가짜 수집·시계·전송을 주입한다. `accounts` 인자를 호환용으로 남겨야 해도 조회·전송 권한으로 쓰지 않으며 M10 호출자와 함께 대조한다. 새 정책·새 CLI를 이 모듈에서 만들지 않는다.

### 4. 단계별 구현 순서

1. **선행 반영 확인:** 설명서 승인, M00 실행기, M01 종료 연결 제거, M03 C9, M07 저장 관측 기반 감시, M08 직접 조회 제거, M10 재열기 정책을 확인한다. Q05는 M03 인계 때 닫고 성공 판정 구현을 시작한다.
2. **완료 영수증 연결:** C9에 따라 `usable_run`·`target_complete`·실행 후 판정을 바꾼다. 목표 거래일·부분 실패·출처·해시를 검사하며 `priority-review.json`을 요구하지 않는다. 과거 영수증은 고치지 않고 현재 성공 증거와 구분한다.
3. **조회와 전송 분리:** `accounts=True` 및 `refresh_account_snapshot` 경로를 제거한다. 감시는 M07이 마지막 저장 관측의 완전성·기준 시각을 판단하게 한다. 전송은 조회 유무와 무관하게 M07 적격 사건·설정을 따르고 전송 실패는 수집 결과를 덮지 않는다. 계좌 실패만을 이유로 한 재수집 분기도 없앤다.
4. **시작과 실행 수명 정리:** 종료 메뉴 이름을 고치고 M10과 인자를 맞춘다. 잠금·같은 모드 재사용·명시적 재시도·자식 수명·종료 코드·비밀값 없는 기록은 유지한다. 등록 스크립트는 고치거나 실행하지 않는다.
5. **격리 검사와 인계:** 합성 root·config·가짜 서비스로 아래 검사를 등록한다. loopback과 가드 상속 fixture 자식은 실제로 검사하되 운영 앱·인증·외부 연결은 쓰지 않는다. M13에 보존할 실행 파일 목록을 전달하고 운영 확인은 §9로 남긴다.

### 6. 검사 명령 (M00 실행기 기준)

§8.2의 확정 형식이다. M00과 M12 구현 뒤 **WB에서** 실행하며, 이번 문서 개정 중에는 실행하지 않는다.

```powershell
.\.venv\Scripts\python.exe -B tests/run_isolated.py --module M12
.\.venv\Scripts\python.exe -B tests/run_isolated.py --module M12 --node test_launch_contracts.LaunchContracts.test_service_results_stay_separate
```

선택 목록은 **`tests/suites/M12.txt`**다. T01~T08의 실제 노드 ID를 적고 전체 자동 발견은 하지 않는다. `--node`는 등록 노드의 부분 확인이며 전체 M12 통과를 대신하지 않는다. 결과 영수증 JSON은 OS 임시 폴더에 둔다. 노드 0개·미등록 선택·가드 사건은 실패이고 차단·skip·미확인을 통과로 합산하지 않는다.

`tests/test_dashboard_startup.py:27`의 loopback은 C8 안에서 검사할 수 있다. `test_dashboard_instance.py:60`, `test_daily_launch.py:161`, `test_worker_lifetime.py:34`의 자식 프로세스도 합성 root와 가드 상속을 먼저 갖춘다. `test_worker_lifetime.py:125`의 운영 config 복사는 금지한다. 보호를 보장할 수 없는 PowerShell 검사는 제외 이유를 결과에 남기고 실제 수명 검증 통과로 바꾸지 않는다.

운영 `dashboard_startup.py`, `daily.ps1`, `scheduled-market.ps1 -Check`, `register-morning-task.ps1 -Diagnostic`은 검사 명령이 아니다. `--offline`은 DB 무변경 보장이 아니며 `-Check`·`-Diagnostic`도 실제 파일 쓰기·예약 등록을 할 수 있다.

### 9. 운영 적용(Claude, 사용자 승인)

모듈 구현 완료와 별개다. Codex 구현 범위에 넣지 않으며 Claude가 사용자 승인 뒤 수행한다.

1. **실제 실행 확인:** 승인된 운영 대시보드·runtime·DB 대조 범위를 먼저 정한다. `--offline --saved-accounts`도 DB에 쓸 수 있으므로 대상의 전후 해시와 바뀐 이유를 기록한다. 구현 시험 결과로 실제 DB 불변이나 운영 기동 성공을 대신하지 않는다.
2. **6단계 예약 전환:** 그때 `register-morning-task.ps1`의 옛 설명·기존 작업 식별 규칙을 검토한다. 실제 예약 상태·실행 인자·숨긴 실행·종료 기록을 확인하고, 등록·재개는 해당 승인이 있을 때만 한다. M12 완료만으로 예약을 켜지 않는다.
3. **운영 결과 분리:** 실제 수집·알림·계좌 조회는 각각 승인된 범위에서만 확인한다. 아침 자동화에는 NH 키가 필요 없으며 계좌는 세션 MCP 관측 저장 경로를 쓴다. 확인하지 않은 항목은 미검증으로 남긴다.
