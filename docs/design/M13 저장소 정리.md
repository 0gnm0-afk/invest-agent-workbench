# M13 저장소 정리

작성·개정: 2026-11-17 · 상태: **초안·§8 반영·사용자 승인 전** · 상세 설계의 모듈 작업 지시서 · 설계 가능성: 설계 가능 · 준비도: 설계 검토 가능

입력: [3단계 설계](<../3단계 설계.md>) §2~4·7·**8(우선)**, [DESIGN-3-20261117](../../DECISIONS.md#design-3-20261117), [SELECT-2-20261117](../../DECISIONS.md#select-2-20261117), [기능 목록](<../2단계 기능 목록 초안.md>), [기술부채 진단](<../2단계 기술부채 진단.md>) DEBT-03C·04, [ver3.1](../투자에이전트ver3.1.md), [용어집](../용어집.md). 추가 근거: [runtime 분류 증거](<../2단계 runtime 분류 증거.md>), [runtime 참조 지도](<../2단계 runtime 참조 지도 초안.md>).

확정은 선행 결정, 권장은 구현 제안이다. 조 5에서 M12와 병렬로 진행한다. M00 실행기, M01 보관 도구·인계 목록, 조 2~4의 참조 목록이 선행 조건이다. 이번 개정은 문서만 수정했으며 아래 구현·시험·운영 적용은 실행하지 않았다.

## 앞 절반 — 설명서

### 1. 하는 일 (세 줄 이내)

종료 기능을 걷어 낸 뒤 남은 실행 자료를 살펴, 보관할 것과 계속 둘 것을 구분한다.
끝난 작업 자료는 압축 보관본이 원본과 같은지 확인한 뒤 정리한다.
실제 자료 정리는 구현 검사와 나누어, 사용자 승인 뒤 Claude가 맡는다.

### 2. 입력과 출력

| 입력 | 출력 |
|---|---|
| M01 인계 목록과 각 기능의 자료 참조 근거 | 보관·보존·판단 보류 목록 |
| 정리 가능한 것으로 확인한 끝난 자료 | ZIP 보관본, 파일별 내용 확인값(SHA-256), 대조 결과 |
| 보호 자료·사용 중 자료·근거 부족 자료 | 보존 이유. 삭제량 목표는 두지 않음 |

2단계의 185행·약 22.5GB는 당시 조사 수치이며 현재 잔여량이나 회수 가능량이 아니다.

### 3. 저장 위치 (C1 소유 테이블·파일)

대상은 워크벤치 `runtime`, 프로젝트 루트 `runtime`과 `llm`이다. 루트 `scripts`는 M01이 맡는다(§8.6). M13이 쓰는 업무 DB 테이블은 없다.

보관 위치는 **권장안** `99.아카이브/09.runtime정리/`다. 구현 검사 자료와 결과는 OS 임시 폴더에만 둔다.

### 4. 다른 모듈과의 연결 (§3 계약 ID 인용)

- **C1(§8.4):** DB 쓰기 함수는 소유 모듈이 맡는다. M13은 DB를 변경하지 않으며 `trade_cycle*` 테이블·데이터도 그대로 보존한다.
- **C8(§8.2):** 구현 검사는 M00 실행기로 합성 자료만 사용한다. 외부 네트워크·운영 자료·인증에 접근하지 않는다.
- M01 보관 도구를 재사용하고, 각 자료의 담당 모듈이 참조 근거를 제공한다. M12의 실행 잠금·현재 실행 기록은 보존한다.

### 5. 이번 개편에서 바뀌는 것 / 그대로인 것 / 없어지는 것

- **바뀌는 것:** 끝난 작업 자료의 보관·보존 이유를 기록하고, 승인된 자료를 검증된 ZIP으로 정리한다.
- **그대로인 것:** DB·인증·보호 원자료·원본 보고서·공시·개인 입력·방법론·계획·과거 snapshot과 사용 중인 자료.
- **없어지는 것:** 운영 적용에서 보관본과 같은 것으로 확인한 지정 파일만. 이름이나 날짜만으로 삭제하지 않는다.

### 6. 쓰는 법 (세션에서·대시보드에서)

세션에서 정리 목록과 보존 이유를 검토한다. 자동 정리 예약이나 새 화면은 없다. 실제 자료 대조·정리는 뒤의 **운영 적용(Claude, 사용자 승인)** 절에서 진행한다.

### 7. 사용자가 직접 확인하는 방법 (5단계 검수에 그대로 쓴다)

가짜 자료로 만든 ZIP의 파일 수·크기·내용 확인값이 원본과 같은지 본다. 보호 자료나 도중에 바뀐 자료는 삭제가 거부되어야 한다. 이 검사 통과와 실제 저장소 정리 완료는 따로 보고받는다.

## 뒤 절반 — 작업 지시서

### 1. 범위와 목표

- **확정(§8.6):** M13 대상은 `WB/runtime`, `P/runtime`, `P/llm`이다. `P/scripts`는 M01 소유다. 기본값은 보존이며 M01의 실제 처리 완료 근거가 있는 경로만 중복 대상에서 제외한다. M01 구현 완료만으로 자료가 정리됐다고 가정하지 않는다.
- **확정(§8.2):** 구현은 합성 자료로 분류·보관·복원·제거 절차를 검증하는 것까지다. 실제 폴더 조사·DB 대조·보관·삭제·대시보드 확인은 §9 운영 적용이며 구현 완료 기준에 넣지 않는다.
- **확정:** M13은 C1의 어떤 테이블도 만들거나 바꾸거나 지우지 않는다. DB 통합·압축·VACUUM, 재수집, 원문을 참조로 바꾸는 이관은 범위 밖이다.

### 4. 단계별 구현 순서

1. **선행 계약 수령.** M00 실행기, M01 보호 목록·보관 함수 계약·인계 문서, 조 2~4의 참조 목록을 받는다. M01의 구현 검사 결과와 실제 자료 처리 영수증을 구분한다. 운영 대상의 현재 상태는 여기서 조회하지 않는다.
2. **합성 분류 사례 작성.** OS 임시 workspace에 WB/runtime·P/runtime·P/llm에 대응하는 가짜 root와 파일을 만든다. 각 항목에 `상대경로 / 생산 모듈 / 소비 모듈 / 생산 코드:줄 / 참조 근거 / 분류 / 제안 처리 / 보류 이유`를 넣는다. 보호·사용 중·생산자 미상·M01 처리 완료·코드만 종료한 자료를 포함한다. 중첩 경로를 중복 집계하거나 혼합 부모를 통째 처리하지 않는다.
3. **공용 보관 호출 연결(권장 계약).** M01의 `archive_retired(manifest, archive_dir, apply=False)`를 재사용한다. 목록 형식은 `module_id=M13`, `source_root`, `entries[]`다. `source_root`는 대상 세 트리 중 명시한 한 곳에 대응하되 구현 검사에서는 임시 root만 쓴다. 각 entry는 `relative_path`, `classification`, `producer_evidence`, `reference_check`, `files[{relative_path,size,sha256}]`를 갖는다. entry 상대경로는 source_root 기준, 파일 상대경로는 entry 기준이다. `reference_check`에는 확인 범위·시점·미해결 참조를 적는다. `archive_dir`와 `apply=False`를 명시하며 기본 호출은 계획만 반환하고 쓰기·삭제하지 않는다.
4. **보존·거부 조건 고정.** 정본 DB·인증·보호 원자료·고정 참조·현재 실행 자료는 제외한다. 생산 종료와 참조 해소가 입증된 종료 작업물만 후보로 삼는다. 원문·과거 버전·DB 의존 JSON·가격 복원 설명 ZIP·원자료성 미확인 LLM 요청/응답은 미해결 상태로 보존한다.
5. **합성 보관·복원·제거 검사.** 임시 ZIP을 닫고 별도 reader로 재열어 경로·개수·크기·파일 SHA를 대조한다. 원본 변경·누락·추가·참조 변경·작성 중·경로 우회 때 제거가 거부되는지 확인한다. 검증한 낱개 파일과 확인된 빈 디렉터리만 제거하고 중단·재개는 같은 계획·보관본 해시를 대조한다.
6. **선택 목록 등록과 인계.** `tests/suites/M13.txt`에 아래 노드를 등록하고 §6 명령으로 검사한다. 결과 영수증은 OS 임시 폴더에 남긴다. 구현 검사 결과와 §9의 운영 적용 대기 항목을 나눠 인계한다. 실제 폴더 조사·DB 대조·대시보드 확인은 수행하지 않는다.

### 6. 검사 명령 (M00 실행기 기준)

§8.2의 확정 형식이다. M00 실행기와 M01 공용 도구, M13 시험 구현 후 **WB 작업 디렉터리에서** 실행한다. 이번 문서 개정에서는 실행하지 않는다.

```powershell
.\.venv\Scripts\python.exe -B tests/run_isolated.py --module M13
.\.venv\Scripts\python.exe -B tests/run_isolated.py --module M13 --node test_runtime_cleanup.RuntimeCleanup.test_archive_round_trip
```

선택 목록은 `tests/suites/M13.txt`다. 일부 검사만 재실행할 때는 `--node 노드ID ...`를 붙이며, 부분 결과로 전체 완료를 대신하지 않는다. 결과 영수증 JSON은 OS 임시 폴더에 둔다.

C8은 임시 합성 파일·DB, loopback(`127.0.0.1`)·socketpair, 같은 가드를 상속한 임시 fixture 자식 프로세스를 허용한다. M13 검사에는 실제 Store 기본 경로·운영 ZIP·실계좌를 넣지 않는다. `records/migrate.py`, `market/retire_history.py`, 실제 대시보드, 예약의 `--check`는 이 검사를 대신하지 않는다. `--offline`도 DB 무변경 보장은 아니다.

### 7. 브랜치·커밋 방법

승인 후 구현은 WB 전용 `module/M13-저장소정리`에서 시작한다. 선행 조의 병합 기준과 기존 변경을 확인하고 M12와 서로 다른 파일만 수정한다. M13 신규 시험·선택 목록만 스테이징해 staged diff를 대조한다. 공용 보관 도구 변경은 M01과 협의한다.

공통 `D:/.git`은 §8.5에 따라 문서와 프로젝트 루트 코드를 담을 수 있지만, M13의 공통 Git 변경 대상은 이 문서뿐이다. runtime·DB·인증·보관 ZIP은 코드 커밋에 넣지 않는다. 이번 문서 개정은 커밋하지 않으며 STATUS·DECISIONS도 수정하지 않는다.

### 9. 운영 적용(Claude, 사용자 승인)

이 절은 **모듈 구현·완료 기준과 별개**다(§8.2). Codex 구현 범위에 포함하지 않는다. 실제 runtime 접근, DB 대조, ZIP 생성·삭제, 실제 대시보드 확인은 Claude가 사용자 승인 뒤 수행하고 전후 해시를 남긴다.

1. **현황과 참조 대조.** M01 실제 처리 영수증을 확인한 뒤 WB/runtime·P/runtime·P/llm의 잔여 목록을 만든다. 코드·설정·DB의 실제 참조를 대조하고 생산/사용 모듈·근거 파일:줄·분류·보류 이유를 적는다. `llm`의 과거 요청/응답은 사용자 입력·과거 판단과의 연결을 확인하기 전 보존한다. M12의 현재 실행 상태는 보존한다.
2. **대상 동결.** 보호 자료·DB·인증·고정 참조를 제외하고 정확한 상대경로 목록과 파일별 크기·SHA를 남긴다. 생산자·소비자·완료 여부가 불명확하면 보류한다. 185행·22.5GB를 현재 대상 수나 회수량으로 쓰지 않는다. 합의한 보관·삭제 목록 안에서만 처리한다.
3. **보관과 제거.** 권장 위치 `P/99.아카이브/09.runtime정리/`에 `M13-대상-YYYYMMDD.zip`, 같은 이름의 `.manifest.json`·`.verification.json`을 만든다. 번호·깊이·중복을 확인하고 기존 파일을 덮어쓰지 않는다. ZIP을 독립적으로 재열어 경로·개수·크기·해시가 원본과 같은지 확인한 뒤, 원본과 참조가 바뀌지 않은 낱개만 제거한다. 작성 중이거나 이를 보장할 수 없으면 보존한다.
4. **운영 결과 대조.** 삭제 전후 파일 수·크기·내용 해시·참조 및 필요한 DB 상태를 대조한다. 실제 대시보드 확인도 이 승인 범위 안에서만 한다. 저장 조회에도 DB 초기화·저장 가능성이 있으므로 전후 해시와 의도한 변경·설명되지 않은 변경을 구분해 남긴다. 설명되지 않은 변화는 확인 완료로 처리하지 않는다.
5. **별도 결과 보고.** 처리·보존·보류 경로, 보관본과 파일별 검증값, 적용 전후 해시를 남긴다. 논리 바이트와 실제 할당 공간을 구분하고, 구현 검사 통과·운영 적용 완료·미검증을 각각 보고한다. 부분 적용을 전체 정리 완료로 표시하지 않는다.
